# Captain decisions — AI-first 重构

日期：2026-10-28  
依据：用户 m03040 的原始目标、SPEC v1.0、AUDIT.md、用户在 2026-10-28 对“逐章写作节奏”的明确选择。

## D1 首次企划只产 P1 + P2

接受。首次企划只生成：
- P1：世界观 / 环境 / 人物
- P2：故事大纲

不生成 P3 章节计划，不写正文。P3 由独立 job 生成并由用户确认；正文只在 P4 生成。现有 `plan.ts` 一次产出 `acts + characters + chapter1` 的行为必须拆开。

## D2 创建即落库并进入流水线页

接受。点击「创建并让 AI 企划」后：
1. 作品立即落库；
2. 关闭新建弹窗并导航到 `/project/:projectId/pipeline`；
3. 企划 job 在后台运行；
4. 关闭页面/刷新不取消 job；
5. 用户回到流水线页能从持久化状态恢复进度。

弹窗内不再等待整份企划。无默认模型/无 Key 时不创建作品，先给前置提示；用户显式选择「先创建，稍后企划」时，创建的是 `draft` 作品，不得伪装成已开始企划。

## D3 阶段确认顺序与 stale 语义

接受。确认顺序固定 P1 → P2 → P3 → P4，服务端二次校验，不允许倒挂。上游结构性变更只把下游标记为 `stale`，不删除下游内容；已确认内容与正文永不因上游变更被静默覆盖。

## D4 P4 逐章写作节奏（用户最新拍板）

**连续生成，全部写完后逐章审。**

- AI 从第一个待写章开始，按 P3 计划连续生成到最后一章；不再要求每章人工 `approved` 才写下一章。
- 用户随时可以「暂停」（当前章写完后停）或「立即停止」（中断当前章并丢弃未完成正文，需二次确认）。
- 全部章节完成后进入逐章审阅：通过 / 退回重写 / 人工编辑后通过 / 跳过。
- 单章失败只影响该章；可从失败章恢复，不重写已完成章。
- 仍保留“重写本章”、版本回滚、字数范围校验。
- `completed` 仍要求所有章进入终态（approved/approved_manual/skipped）。

这条覆盖 SPEC §4.5 中“逐章停在 in_review 等 REVIEW”的默认描述；P4 的暂停/停止、逐章审阅、失败恢复仍按 SPEC 其余条款执行。

## D5 SPEC §14.2 默认答案

接受 Q1–Q7 的建议默认值，除 Q2（自动连写）按 D4 解释为：连续生成是默认，但仍保留人工逐章审阅，不提供“AI 自动通过所有章”的托管模式。Q4 的“只导出大纲/设定”列为 V1 可选，不阻塞主流程。

## 对下游的硬要求

- UX：按“连续生成 + 全部写完再逐章审”设计 P4 页面；进度必须能显示当前章/总章数、暂停/立即停止、失败章恢复。
- 架构：P4 job 是连续循环，不是“每章结束等前端确认”的状态机；人工审阅在 job 完成后进行。
- 后端：不要为每章设置“未 approved 则下一章不生成”的阻塞；保留单章失败隔离与恢复。
- 前端：章节列表状态在生成中为 generating/queued，写完后统一转 in_review；不得把“未审”误判为“不可继续”。
- QA：S1 长篇黄金路径改为连续写完全部章，再逐章通过；另测暂停/立即停止/单章失败恢复。

## D6 REVIEW 四键只在写作台

接受 UX 的约束：审阅的通过/退回/人工通过/跳过只在写作台渲染；流水线章节板只保留「审阅」导航，不在章节行就地放四键。这样 `chapter-approve` 等锚点全站同页唯一，QA 不用 `.first()` 兜底。QA 的 S1 步骤 8–10 按 UX-SPEC §7.9 改写：先连续写到 `in_review`，再进入写作台逐章审。

## D7 `nextStep` 由服务端下发

接受。`PipelineSnapshot.nextStep` 是唯一判定源，前端只渲染文案与跳转，禁止再写一套客户端阶段判定。服务端要处理 blocker、review 计数、持久化 lastError；前端不重算。

## D8 P3 目标字数自动分配（对应 UX D9）

接受 UX D9，提供「按目标字数分配」动作；但必须是显式操作 + 分配预览，用户确认后才覆盖每章 target，不能静默重算用户手改过的字数。分配失败或总目标超出 ±25% 时仍按 UX-SPEC 的偏差规则要求显式接受。
