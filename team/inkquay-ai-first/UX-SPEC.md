| | 内容 |

### 0.1 与 SPEC 的关系

1. SPEC 定"必须发生什么"，本文档定"用户在哪看到、点什么、看到什么字"。凡本文档新增的**视觉/交互细节**（如左栏阶段轨道、审阅队列模式、按目标字数分配），都在 §15 列为待决项并给默认建议，不擅自扩需求。
2. SPEC §11 的 34 个 `data-testid` **一个不改名**；本文档给每个锚点指定唯一宿主组件与可见条件（§13）。需要新增锚点的，集中在 §11.4 提案，等 QA 对齐后再实施。
3. SPEC §6.2 四态、§7.1 错误分类、§10 数字全部照抄，本文档只做"界面映射"。

### 0.2 D4 覆盖声明（重要）

用户已拍板 **P4 = 连续生成，全部写完后逐章审**。因此：

| SPEC 原文 | 本文档按 D4 的处理 |
|---|---|
| §4.5「连续生成（从第一个 pending 起逐章生成，逐章停在 `in_review` 等 REVIEW）」 | 改为**连续生成到最后一章**，中途不等待人工通过；写完后进入"待审阅"批量审阅队列 |
| §4.5「确认门槛：每章必须人工终态」 | **保留**（终态仍需人工：approved / approved_manual / skipped） |
| §12.1 S1 步骤 8–9（每写完一章就 approve / request-changes） | 需按 §7.9 修订：先连续写完，再逐章审 |

`in_review` 的语义在 D4 下 = **"已生成、待人工审阅"**，**不再是"阻塞下一章的门"**。这一点决定了两条界面禁令（§7.2）：禁止把"未审"渲染成"不可继续"；禁止出现"等待你通过才能继续写"的文案。

## 1. 设计原则

七条，每条都附一条**禁令**，因为过去的问题恰恰是"没有禁令"。

**P-1 一屏永远能回答三个问题：我在哪、进度多少、下一步点哪。**
左侧阶段轨道 + 顶部 job 条 + 底部下一步按钮，三者**同时可见**（不靠滚动）。
禁令：任何页面不得出现"只有 spinner、没有阶段名、没有秒数"的中间态（AUDIT R1/R2 的直接病灶）。

**P-2 先落库，再干活；页面是 job 的观察窗，不是 job 的宿主。**
创建即跳转，job 后台跑，关页面不取消（INV-5）。
禁令：禁止把长任务做成"一次 `await` 撑住整个页面"；禁止在弹窗里等 40 秒。

**P-3 门槛必须"看得见 + 可解释 + 一步可达"。**
未满足的确认按钮**不禁用成灰块**，而是禁用 + 旁边列出 blocker 文本 + 每项可点击跳转到问题处。
禁令：禁止"按钮灰掉但不说明原因"（AUDIT R1 的同族错误：把原因藏在不可达的分支里）。

**P-4 AI 的每次输出都是可回滚的修订，人工改的内容永不被静默覆盖。**
所有 AI 动作（整份重生成、块重生成、条目重生成、按意见重做）都产生新修订，操作前自动快照。
禁令：禁止无版本覆盖；禁止"重新生成"按钮在有确认内容时无二次确认直接冲掉。

**P-5 范围必须写在按钮上。**
"给 AI 提意见"分四个作用域（条目 / 块 / 阶段 / 章），提交前必须显示"这次会重做 1 条"还是"整份 12 条"。
禁令：禁止一个"重新生成"按钮在三个位置做三件不同的事却叫同一个名字。

**P-6 长任务的三种"停"必须分清：暂停（安全）、立即停止（丢当前章）、离开（什么都不丢）。**
三者在界面上是三套文案、三种确认策略（§7.4、§9.5）。
禁令：禁止把"暂停"做成"停止"，禁止离开时弹"会中断生成"（那是假警告，job 不会中断）。

**P-7 空态必须有出口。**
每个空态 = 一句话说明为什么空 + 一个主操作按钮。
禁令：禁止裸空态（只有"暂无内容"四个字）；禁止空态里放"稍后自行填写"当唯一出路。

## 2. 信息架构

### 2.1 全局骨架（完全复用现有 AppShell，不新造视觉语言）

```
┌──────┬──────────────────┬────────────────────────────────────────────────────────┐
│ Rail │  Panel 292px     │  Topbar 58px                                           │
│ 78px │  （随页面换内容）│────────────────────────────────────────────────────────│
│      │                  │  JobBar（有 job 时出现，44px，可折叠）                 │
│ 书房 │                  │────────────────────────────────────────────────────────│
│ 作品 │                  │  Banner 区（stale / interrupted / legacy / failed）    │
│ 设定 │                  │────────────────────────────────────────────────────────│
│ 统计 │                  │  View：阶段工作区（可滚动）                            │
│      │                  │                                                        │
│      │                  │────────────────────────────────────────────────────────│
│      │  PanelFoot       │  Sticky 确认条（阶段门槛 / 下一步）                    │
└──────┴──────────────────┴────────────────────────────────────────────────────────┘
```

- 复用类名：`.rail`、`.panel`、`.main`、`.topbar`、`.viewport`、`.view`、`.view-head`、`.view-sub`、`.eyebrow`。
- 复用组件：`AppShell`、`Cover`、`Icon`、`Toast`、`EmptyState`（现有 `.empty-state`）、`pbar`、`segmented`、`chip`、`tag`、`modal`、`overlay`、`danger-confirm`、`toast--warn`。
- **不新增**：新的配色、新的圆角体系、新的阴影。新增只在 `.pipeline-*` 命名空间内加布局与状态色（§11.3）。

### 2.2 导航与路由

**顶栏 tab 按作品形态区分（这是一处 IA 修正，理由在下方）。**

| 作品形态 | 顶栏 tabs | 说明 |
|---|---|---|
| 新流程长/短篇（`pipelineStatus` 存在） | `企划` · `正文` | 企划 = `/project/:id/pipeline`；正文 = `/project/:id`（写作台，P4 编辑器） |
| 旧作品（legacy，无 pipeline 数据） | `正文` · `大纲` · `设定` | 完全保持现状，不打扰存量用户 |
| 剧本 | `正文` · `场景` | 保持现状，**不进流水线**（SPEC 2.3 #7） |

**路由表（只增不改，R7）**

| 路由 | 页面 | 状态 |
|---|---|---|
| `/` | 书房（作品库） | 改：卡片加「企划未完成 / 待审阅」徽标 + 继续入口（§9.1） |
| `/project/:projectId/pipeline` | **流水线页（新）** | 新增 |
| `/project/:projectId` | 写作台（P4 编辑器 + REVIEW 条） | 改：加 REVIEW 条、`plan-progress` 顶部条；其余不动 |
| `/project/:projectId/outline` | 旧大纲页 | **仅 legacy 作品可达**；新流程作品重定向到 `/pipeline?stage=p2` 并 toast「大纲已并入企划」 |
| `/project/:projectId/codex` | 旧设定页 | 同上 → `?stage=p1` |
| `/project/:id/screenplay`、`/settings` | 不变 | — |

**为什么旧页在新流程作品上重定向，而不是保留双写**：SPEC §14.1 第一条风险就是"两条链路并存 → 内容分裂"。设定/大纲在流水线页有"块 + 意见 + 历史 + 锁定 + 确认"这些旧页没有的能力，若两边都能写，用户会在大纲页改完 P2 却在企划页看不到"未确认"状态。重定向是最小代价的收口。

### 2.3 页面地图

```
书房 ──新建作品（弹窗）──► 流水线页 /pipeline
  │                         ├─ P1 设定（世界 / 环境 / 人物）
  │                         ├─ P2 故事大纲（幕 / 节拍）
  │                         ├─ P3 章节计划（章节表 / 节拍计划）
  │                         └─ P4 逐章写作（控制条 + 章节板）
  │                               └─点某一章──► 写作台 /project/:id?chapter=&review=1
  │                                                └─ REVIEW 条（通过 / 退回 / 人工通过 / 跳过 / 重写）
  └─旧作品──► 写作台（现有四页，不变）
```

**流水线页是单路由 + 内部阶段切换**（不是 `/pipeline/p1` 四个路由）。理由：① R7 只允许新增一个路由；② 阶段间切换要保留左栏轨道与 job 条，多路由会重建 shell，刷新成本高；③ 阶段用 `?stage=p1|p2|p3|p4` 记录，刷新/分享可定位（不影响路由契约）。

### 2.4 三种形态的 IA 差异（一张表看完）

| | 长篇 | 短篇 | 剧本 |
|---|---|---|---|
| 阶段 | P1 → P2 → P3 → P4 | P1 → P2 → P3 → P4 | 不进流水线 |
| P2 结构 | 幕（2–12）→ 幕下节拍 | 节拍组 → 节拍（6–40），**不出现"幕"字** | — |
| P3 名称 | 章节计划（3–200 章） | **节拍计划**（3–40 节拍，默认 8） | — |
| P3 单元 | 章，字数默认 2,500–4,000 / t3,000 | 节拍，默认 800–2,500 / t1,500 | — |
| P4 名称 | 逐章写作 | **逐节拍写作** | — |
| P4 单元 | `chapter-row` | `beat-row`（`chapter-row` 计数必须 = 0） | — |
| 正文组织 | 卷 / 章 | 单篇：节拍按序拼接，导出一个 md | — |
| 卷 UI | 有 | **不渲染任何卷/章结构** | — |

### 2.5 文案词表（同义词一律禁止）

| 概念 | 唯一叫法 | 禁止 |
|---|---|---|
| 阶段 | 阶段 1..4 + 名称：`设定` / `故事大纲` / `章节计划`（短篇 `节拍计划`）/ `逐章写作`（短篇 `逐节拍写作`） | 步骤、环节、Step、Phase |
| 生成任务 | **生成任务**（口语可用"正在生成"） | 任务、job、进程、批处理 |
| 阶段状态 | `待生成` `生成中` `待确认` `已确认` `生成失败` `已跳过` | 完成、进行中、草稿、draft |
| 章节状态 | `待写` `生成中` `待审阅` `已通过` `需修改` `人工通过` `已跳过` | 完成、已写、成功 |
| AI 动作 | `重新生成`（作用域+）、`按意见重做`、`重写本章`、`扩写`、`精简` | 刷新、再来一次、重生 |
| 人工动作 | `确认`（阶段）、`通过`（章）、`退回重写`、`人工通过` | 提交、审核、验收 |
| 意见 | **意见**（"给 AI 提意见"） | 提示词、feedback、指令 |
| 版本 | **修订**（列表叫「修订历史」）；章正文的版本叫「版本」 | 快照、历史记录 |
| 上游变更 | `上游已变更`（横幅） | 过期、过期数据、失效 |

## 3. 第一屏：新建作品之后落在哪

### 3.1 时序（照 SPEC §6.1 实现，这里补界面）

| 时刻 | 界面 | 锚点 |
|---|---|---|
| t=0 | 点「创建并让 AI 企划」 | `new-project-submit` |
| t≤300ms | 按钮 disabled，文案 `正在创建…`，弹窗内表单只读 | — |
| t≤500ms | 弹窗关闭 → push `/project/:id/pipeline` → **首屏即渲染完整骨架**（左栏轨道 + job 条 + P1 骨架 + 秒数），此时 job 才刚 running | `plan-progress[data-state=running]` |
| 0.5–15s | job 条：`正在生成设定… · 12 秒 · 取消`；P1 视图显示 3 个块骨架（每块标题在先，内容占位） | `plan-cancel` |
| t≈15s | job 条下方追加提示条（`.pipeline-hint`）：`生成通常需要 20–60 秒 · 可以先离开，作品已保存` | — |
| done | P1 `待确认` + 顶部 toast/横幅 `AI 企划完成，请审核设定`；P2 已生成（`待确认`，确认按钮按 R6 置灰并显示"请先确认设定"） | `stage-p1[data-status=review]` |
| failed | 错误卡（§9.2）替换 P1 内容区，保留左栏轨道 | `plan-error[data-code]` |
| cancelled | `已取消企划` 提示卡 + `继续企划` / `先自己写` | `plan-progress[data-state=cancelled]` |

关键：**首屏不等待数据**。路由跳转后立刻用已有 project 基本信息（标题、类型、目标字数、默认模型）渲染骨架，stage/job 详情用 2s 轮询补齐。禁止"白屏等接口"。

### 3.2 W1 线框：创建后第一屏（P1 生成中）

```
┌──────────────────────────────────────────────────────────────────────────────────────┐
│ Rail │ ╭ 阶段轨道 ╮            │ ← 修仙日常  [长篇小说]                        ⋯ 设定 │
│  书  │ │ 企划进度 1/4 已确认  │  ┌─────────────────────────────────────────────────┐  │
│  作  │ │                     │  │ ◐ 正在生成设定…            12 秒      [取消企划] │  │  ← JobBar
│  品  │ │ ● 1 设定    [生成中]│  ├─────────────────────────────────────────────────┤  │
│  设  │ │ ○ 2 故事大纲        │  │ 生成通常需要 20–60 秒 · 可以先离开，作品已保存    │  │  ← ≥15s
│  定  │ │ ○ 3 章节计划        │  ├─────────────────────────────────────────────────┤  │
│      │ │ ○ 4 逐章写作        │  │ 阶段 1 · 设定                                   │  │
│      │ │                     │  │ 世界观、环境与人物                              │  │
│      │ │ ─────────────────── │  │ AI 正在生成初稿，产出会先作为待确认修订          │  │
│      │ │ 下一步              │  │ ┌─────────────────────────────────────────────┐ │
│      │ │ 等待 AI 完成设定    │  │ │ 世界观                              ▓▓▓░░  │ │
│      │ │ [取消企划]          │  │ └─────────────────────────────────────────────┘ │
│      │ │                     │  │ ┌───────────────────┐ ┌───────────────────┐    │
│      │ │ ─────────────────── │  │ │ 环境                │ │ 人物              │    │
│      │ │ 生成记录 ›          │  │ │ ▓▓▓░░ 生成中…       │ │ ░░░░░ 排队中      │    │
│      │ ╰─────────────────────╯  │ └───────────────────┘ └───────────────────┘    │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

**已确认项（`已完成`）怎么显示**：左栏每个阶段行的右侧徽标（`待生成 / 生成中 / 待确认 / 已确认 / 生成失败 / 已跳过`），加上副文案的量化摘要——这是"已完成项"最省空间的表达：

```
● 1 设定            已确认
  3 条世界规则 · 2 环境 · 12 人物
○ 2 故事大纲        待确认
  3 幕 · 14 节拍
○ 3 章节计划        待生成
○ 4 逐章写作        待生成
```

**规则**：
- 轨道每行可点（`待确认`/`已确认`/`生成失败` 可进；`待生成` 且上游未确认 → 可进但视图是锁定态 + 说明，不是死链）。
- 当前阶段行加 `.is-current`（左侧 3px accent 竖条 + 文字提亮）。
- 顶部一行常显 `企划进度 2/4 已确认`（`已确认 + 已跳过` 计数）。
- `生成失败` 行带 `!` 徽标（`.pipeline-rail__badge--failed`），确保用户从任何阶段都能看到"有个阶段挂了"。

### 3.3 「下一步」模型（左栏底部卡片）

一行判定，按序取第一个命中：

| 条件 | ＣTA 文案 | 行为 |
|---|---|---|
| P1 `待生成` | `让 AI 生成设定` | 启动 P1 job |
| P1 `待确认` | `审阅并确认设定` | 滚到确认条 + 高亮 blocker |
| P1 已确认 & P2 `待确认` | `审核故事大纲` | 切 `?stage=p2` |
| P2 已确认 & P3 `待生成` | `生成章节计划` | 启动 P3 job |
| P3 `待确认` | `检查章节字数并确认` | 切 p3 + 聚焦 `chapter-plan-total` |
| P3 已确认 & P4 无终态 | `开始连续写作` | `write-start` |
| P4 `生成中` | `查看写作进度`（附 `12/37`） | 聚焦 job 条 |
| P4 `已暂停` | `继续写作` | `write-continue` |
| P4 全部写完待审 | `开始逐章审阅（25 章待审）` | 跳写作台 `review=1` |
| 全终态 | `导出成稿` + `去正文` | 现有导出能力 |

**禁令**：不得在"下一步"卡里一次给 3 个同等权重的按钮——一个主按钮 + 至多一个文字链。

### 3.4 与 AUDIT 的对照（为什么要这么设计）

| AUDIT 病灶 | 本设计的对应 |
|---|---|
| R1 主按钮与"AI 正在企划…"被同一条件隐藏 | 骨架先渲染，主按钮区域变成 job 条（独立组件，不依赖 `created` 布尔） |
| R2 无进度通道 | job 条（阶段名 + 秒数 + 取消）+ 阶段内块级进度 |
| R3 无重试无降级 | 失败卡三按钮（重试/换模型/删作品），错误码 18 类映射 |
| R4 失败留空壳 | 首屏左栏 `待生成` + 轨道，空壳=无害的"0 内容"，且失败卡提供"删除作品" |
| R6 失败无痕 | `lastError` 持久化 → 刷新后 `plan-error` 重现 + 作品库卡片「企划未完成」 |

### 4.2 三个块（block）的边界与数据

| 块 | 承载 | 单元（`item-card` 的 `data-kind`） | 条目数要求 |
|---|---|---|---|
| 世界观 | 4 个字段（时代地点 / 世界规则 / 基调母题 / 语言称谓） | `world`（**整块算 1 个条目**） | 长篇：世界规则必填 ≥1 条；短篇：可空（默认勾"不需要"） |
| 环境 | 场景/场所列表 | `env` | ≥1 |
| 人物 | 主角（唯一）+ 配角 | `character` | ≥1 |

**为什么世界观是"1 个条目 4 个字段"而不是 4 个条目**：世界观的重生成与确认是整体语义（改世界规则必然牵动语言称谓），拆成 4 条目会让"给 AI 提意见"的作用域变成四个按钮。字段级仍可编辑，但保存是整块原子提交（一次产生 1 条修订）。

### 4.3 条目卡的三态

| 态 | 视觉 | 可见操作 | 备注 |
|---|---|---|---|
| **摘要态**（默认） | 名称 + 一行摘要 + 2–3 个 chips；主角卡有 ★ 与 accent 左边框 | 编辑 / 重生成 / 提意见 / 历史 / 锁定 / 删除 | 悬停整卡高亮，`⋯` 菜单常显在触控/键盘模式 |
| **编辑态** | 原地展开成表单（不跳页、不开新弹窗） | 保存 / 取消 / 重置为当前修订 | 字段以 SPEC §4.1 为准；字数上限：角色摘要 ≤ 200 字，环境一句话 ≤ 60 字（超限提示不阻断） |
| **生成中** | 卡片内容 40% 不透明度 + 顶部 2px 进度条 + 文案 `正在重写…  8 秒` | 取消（卡片右上角 `✕`） | 只重做这一条时使用；旧内容仍在下方可见（禁空白） |

**编辑态的保存语义**（对齐 INV-2）：
- 点「保存」→ `PATCH item` → 服务端写 1 条 `manual` 修订 → 卡片回摘要态，toast `已保存`，页脚保存状态区（复用 `.tb-save`）显示 `已保存`。
- 保存失败 → 卡片**保持编辑态**、内容不丢、底部错误条 `保存失败：<人话>` + `重试`。
- 离开页面/切换阶段时有未保存编辑 → 触发离开确认（§9.6）。

### 4.4 重新生成：三个作用域，三个不同的按钮文案

这是 P-5 的落地。**按钮文案必须带范围**，且提交前显示影响面。

| 入口 | 按钮文案 | 范围 | 影响 | 二次确认 |
|---|---|---|---|---|
| 条目卡 `⋯` → 重生成 | `重生成此条` | 1 个条目 | 该条目新修订，旧版本保留 | 否（可回滚） |
| 块头 | `重生成此块` | 该块内未锁定条目（如人物块 12 条中 11 条未锁） | 批量新修订 | **是**（若块内已有确认内容→先提示"会重做 11 条，3 条已锁定不动"） |
| 阶段头 | `整份重新生成` | 全部三块 | 全量新修订 | **是**，对话框列出 `将重做 12 人物 / 2 环境 / 世界观；3 条锁定不动` |
| 阶段头 | `给 AI 提意见` | 见 §4.5 | 按意见重做 | 提交前显示范围 |

**锁定（`item-lock`）**：默认未锁。锁定后：块级/阶段级重生成**跳过**该条（按钮文案与确认框里的计数必须体现"锁定不动"）；条目级重生成仍可手动执行。
S1 场景要求的"已锁章不受预设影响"在 P3 对应实现，P1 这里是同一语义的条目版。

### 4.5 给 AI 提意见：四个入口 + 一个共用组件

**入口分布（同一组件，四个作用域）**

| # | 入口位置 | 作用域 | 提交后 | 典型用法 |
|---|---|---|---|---|
| 1 | 条目卡 `⋯` → 提意见 | 单条目 | 只重做该条目；其余不动 | "改成她的妹妹" |
| 2 | 块头 → 本块意见 | 块内未锁条目 | 重做该块 | "三个人物动机太像，拉开差异" |
| 3 | 阶段头 → 给 AI 提意见 | 三个阶段全部（未锁） | 整份重做 | "整体再阴冷一点，减少人物" |
| 4 | P4 章内 → 退回重写 | 单章 | 按意见重写该章（新版本） | "对话太多，压到 1500 字，结尾加钩子" |

**组件 `FeedbackComposer`（抽屉，右侧 480px）**

```
┌─ 给 AI 提意见 ──────────────────────────────── ✕ ┐
│ 作用范围  ⦿ 只重做这一条：沈砚                    │  ← chip 形态，不可改（由入口决定）
│           ○ 整块：人物（11 条未锁 + 1 条锁定不动） │
│                                                   │
│ 你想怎么改？                                      │
│ ┌───────────────────────────────────────────────┐ │
│ │ 把沈砚改成一个不肯承认自己在等信的人，          │ │
│ │ 把"执拗"换成"闪躲"                              │ │
│ └───────────────────────────────────────────────┘ │
│ 快捷： [减少人物] [动机拉开差异] [更阴冷] [加悬念]  │
│                                                   │
│ ℹ 会生成 1 条新修订，当前版本保留可回滚            │
│                             [取消]  [交给 AI 重做] │
└───────────────────────────────────────────────────┘
```

**规则**
- 范围单选**只在该入口允许多个范围时**出现（如阶段头允许"整份"或"只改某一块"）；条目卡入口只显示不可改的范围 chip。
- 意见必填，< 6 字时主按钮置灰 + 提示 `说清楚一点，AI 才知道往哪改`（不硬限制长度，仅防误点空提交）。
- 提交后：抽屉关闭 → 对应卡片/块进入生成中态 → job 条显示 `正在按你的意见重做（人物 · 1 条）`。
- 完成后：块头出现**变更摘要条**（`.pipeline-changes`）+ 撤销：
  `AI 改了 3 条：[沈砚] 动机改为闪躲 · [陈丽] 补充护短 · [老周] 删去… [撤销这次重做] [查看修订]`
  撤销 = 恢复到这次操作前的修订（可回滚，非删除历史）。
- 每次反馈都写 Revision，`note` = 用户原文；`item-history` 里能读到意见原文（引用块）。

### 4.6 生成中 / 取消 / 失败（阶段内，不是整页）

| 场景 | 界面 | 锚点 |
|---|---|---|
| 块生成中 | 块内进度条 + `正在重做（3/5）· 12 秒` + 块右上 `取消` | — |
| 阶段生成中 | 骨架 + 阶段头 `正在生成…`；job 条同步 | `stage-p1[data-status=generating]` |
| 取消（块级） | 卡片回退到上一修订，toast `已取消，内容未变` | — |
| 取消（阶段级） | 保留已完成块的产物（未确认修订），失败步骤零写入（INV-3） | `plan-progress[data-state=cancelled]` |
| 单个条目失败 | 卡片右上 `!` + 行内文案 `这一条没生成成功（供应商超时）[重试]`；**其余条目不受影响** | — |
| 阶段失败 | 阶段内容区顶部错误卡（§9.2），下方旧内容照常可读可编辑 | `plan-error[data-code]` |

**禁令**：失败时不得清空已有内容；不得把失败静默成"空块"。

### 4.7 修订历史（W4，抽屉）

条目级 `item-history` 与阶段级 `修订历史` 是同一个组件 `RevisionDrawer`，只是过滤范围不同。

```
┌─ 修订历史 · 沈砚 ───────────────────────────────────────────── ✕ ┐
│ ┌ 时间线 ─────────────────────┐ ┌ 预览（只读）───────────────────┐ │
│ │ ● 按意见重做   22:41        │ │ 沈砚 · 主角                   │ │
│ │   "改成她的妹妹"            │ │ 邮局分拣员，28 岁             │ │
│ │   动机：执拗 → 闪躲         │ │ 动机：闪躲（原：执拗）         │ │
│ │ ○ 你修改       22:38        │ │ ⋯                             │ │
│ │ ○ AI 初稿      22:31        │ │                               │ │
│ │ ○ 确认快照     22:35  🔒    │ │                               │ │
│ └─────────────────────────────┘ └───────────────────────────────┘ │
│ 差异高亮：新增绿底 / 删除删除线 / 改写双色                            │
│                              [恢复到此版本]  [复制内容]  [关闭]      │
└────────────────────────────────────────────────────────────────────┘
```

- 时间线元素：来源徽标（`AI 初稿` `你修改` `按意见重做` `整份重生成` `回滚` `确认快照`）+ 时间 + 一句话摘要 + 字数/字段变化。
- 默认选中"当前版本"，右侧显示与上一版的 diff；点任一条 → 右侧预览该版本，diff 对比"该版本 vs 当前版本"。
- 「恢复到此版本」= 生成一条新修订（来源 `回滚`），**不删除**中间历史；二次确认文案：`回到 22:31 的版本？当前版本会保留在历史里。`
- 空态：`还没有历史。AI 生成、你编辑或确认后，这里会记录每一条修订。`
- 阶段级历史额外带"确认快照"分组（INV-2：确认快照永不清）。

### 4.8 确认门槛与 blocker

「确认设定」= `stage-confirm`。禁用条件与文案一一对应（`stage-confirm-blockers` 文本，逐项可点）：

| blocker | 文案 | 点击行为 |
|---|---|---|
| 人物 0 | `人物至少 1 个` | 滚到人物块 + 高亮「新增人物」 |
| 环境 0 | `环境至少 1 个` | 滚到环境块 |
| 世界规则为空（长篇） | `世界观需要至少 1 条世界规则` | 滚到世界观 + 进入编辑态 |
| 生成中 | `还有生成任务没结束` | 聚焦 job 条 |
| 上游未确认（P2 用） | `请先确认设定` | 切到 `?stage=p1` |

- 全部满足：按钮变主色 + 文案 `确认设定，进入故事大纲`。
- 点击后：`stage-p1[data-status=confirmed]`，确认条变成一行 `已确认 · 22:35 · 12 人物 [取消确认并继续编辑]`。
- **确认后继续编辑**：SPEC 3.2 允许 `confirmed → review`。界面上任何编辑/重生成都让状态回 `待确认`，并在确认条提示 `内容已变更，需要重新确认`。不弹窗打断。

### 4.9 跳过（仅 P1）

`stage-skip` 出现在阶段头 `⋯` 菜单里，文案 `跳过设定，我自己写`。二次确认：`跳过设定后，P2/P3 会缺少人物与世界观上下文，AI 生成质量会明显下降。` 确认后 `stage-p1[data-status=skipped]`，左栏徽标 `已跳过`，并给一次性可撤销提示（7 天内可 `取消跳过`）。

### 6.2 表格字段与交互

| 列 | 交互 | 校验（阻止确认，不阻止编辑） |
|---|---|---|
| `#` 序号 | 只读；拖拽手柄在行首（拖动排序=结构性变更→下游 stale） | 连续 1..N |
| 章节标题 | 行内 input（宽度自适应，≤ 40 字） | 非空 |
| 功能 | chips 多选（预设：`推进主线 / 揭示信息 / 关系变化 / 铺垫伏笔 / 回收伏笔 / 冲突升级 / 高潮 / 收束 / 过渡`），管理自定义 | ≥1 |
| 大纲 | 显示 2 行截断；点击开右侧抽屉编辑（长文本 300–800 字） | 非空（≥ 30 字提示） |
| 字数 | 三个数字输入 `min / target / max`，紧凑排列（`300/2000/4000`） | `min ≥ 300`、`max ≤ 20000`、`min ≤ target ≤ max` |
| 状态 | 徽标：`待写` `写作中` `待审阅` `已通过` `需修改` `已跳过`（读 P4 真实状态） | — |
| 锁定 | 图标按钮切换 `data-locked` | 锁定行不被预设/按目标分配/整份重生成改动 |

**数字输入的一个已知坑（务必按此实现）**：`el-input-number` 类控件默认值写 `0` 会让用户不改直接提交时静默写入 0；本项目 P3 的字数三连必须默认 `null`，`onChange` 时空字符串视为 `null`，`0` 视为非法（提示 `字数不能为 0`），提交前分开判 `null` 与 `0`。（对应记忆里"0 与未填必须在组件层区分"。）

**行数多时**：> 30 行启用虚拟滚动（复用现有列表滚动容器）；表头 sticky；提供筛选 `未锁定 / 已锁定 / 已写 / 需修改`。

### 6.3 章节数调整（`chapter-plan-count`）

改数字后不立即生效，而是给出**变更预览**再确认——因为增删章是结构性变更（会牵动已有正文与下游）：

```
┌ 章节数 40（当前 37）──────────────────────────────────┐
│ 将新增 3 章（第 38–40 章），按当前预设生成计划           │
│ 新增章状态：待写                                        │
│                                    [取消]  [应用并生成] │
└─────────────────────────────────────────────────────────┘

┌ 章节数 30（当前 37）──────────────────────────────────┐
│ 将从末尾删除 7 章（第 31–37 章）                        │
│ ⚠ 第 31–33 章已有正文（共 9,120 字），不能通过减少章数删除 │
│ 可选：① 只删到 33 章  ② 先删除正文再减少章数             │
│                              [取消]  [只删空白章]       │
└─────────────────────────────────────────────────────────┘
```

规则：
- **增章**：调用 P3 增量生成（只产新增章），旧章（含锁定/已写）一条不动。
- **减章**：从末尾往前删；碰到 `已写/待审阅/已通过/需修改` 的章立即停手并给出上面那个提示。**绝不静默删除正文**。
- 应用后：右栏轨道摘要与顶部汇总即时更新；若已有正文 → 顶部 `stale` 横幅（P4 已写内容不受影响，R1）。

### 6.4 字数范围、总字数估算与三档预设

**估算口径（写死，别各页各算）**：
- 计划合计 = `Σ target`（不是区间中值、不是 min/max 之和）。
- 目标 = 作品 `goalWords`。
- 偏差 = `(Σtarget − goal) / goal × 100`，1 位小数带符号。
- 阈值 ±25%（SPEC §10.1）：`|偏差| ≤ 25%` 绿色 `按计划可达成`；超出橙/红并**要求显式接受**（`接受偏差` 按钮 → 打标 `deviationAccepted=true`，写库，刷新后仍生效）。

**三档预设（`chapter-plan-preset`）**，点击即批量应用：

| 预设 | 长篇 min/t/max | 短篇 min/t/max | 作用范围 |
|---|---|---|---|
| `快`（长篇）/ `极短`（短篇） | 1500 / 2000 / 2500 | 500 / 900 / 1200 | 未锁定的所有章 |
| `标准` | 2500 / 3000 / 4000 | 800 / 1500 / 2500 | 同上 |
| `厚重` / `舒展` | 4000 / 5000 / 6000 | 1500 / 2500 / 3500 | 同上 |

应用前必须显示影响面：`将对 34 章应用「标准」，3 章已锁定不变`（toast 或浮动提示，5s 消失）。应用后 `chapter-plan-total` 立即重算。

**「按目标字数分配」**（本 UX 建议新增的能力，列为待决 D9，见 §15）：
当偏差超出 ±25% 时，逐章手改 37 个数字不现实。按钮行为：按比例重算未锁定且无正文的章的 `target`（保持各自 min/max 相对关系），预览 `将调整 34 章，3 章锁定/已写不动`，确认后应用。
若 captain 不采纳，则替代路径是"只允许用预设 + 接受偏差"，界面必须保留 `接受偏差`，否则用户被卡死。

## 7. P4 逐章写作（按 D4：连续生成 → 全部写完 → 逐章审）

> **本节的语义基线**：AI 从第一个 `pending` 章起，**一路连续生成到最后一章**，中途不等待人工通过；全部写完后进入"待审阅"，再逐章人工终态。`in_review` = 已生成待审，不是阻塞门。

**行操作按状态给**：

| 行状态 | 主操作 | 次操作（`⋯`） |
|---|---|---|
| `pending` 未排队 | `立即写本章`（单章 job） | 查看大纲 / 调整字数 / 跳过本章 |
| `pending` 排队中（`data-queued=true`） | `插队先写这一章` | 查看大纲 |

| `in_review` | `审阅`（跳写作台） | 重写 / 扩写 / 精简 / 跳过 / 版本 |
| `changes_requested` | `按意见重写` | 查看意见 |
| `approved` / `approved_manual` / `skipped` | `查看` | 我要改（回 `in_review`） |

### 7.2 控制条状态机（`write-*` 四个锚点 + 文案）

`data-state` **只取 SPEC §11 允许的四个值**：`idle | running | paused | interrupted`（不新增状态值，QA 的契约不许改）。
细分态放附加属性 `data-phase`：`idle | running | pause-requested | paused | stopping | stopped | done | failed`，并配 `data-pause-pending`（布尔）与 `data-failed-chapter`（章号）。

| 状态 | 可见主按钮 | 文案（必须逐字出现的关键词） | 其它按钮 |
|---|---|---|---|
| `idle` | `write-start`：`开始连续写作` | `待写 25 章，AI 会从第 1 章连续写到第 37 章` | — |
| `running` | `write-pause`：`暂停` | `正在写第 13/37 章《纺织厂的雨》· 已 1,840 字 · 已用 12 分 40 秒` | `write-stop`：`立即停止` |
| `pause_requested` | `write-pause` 置灰，文案 `本章写完后暂停` | `正在写第 13/37 章 · 写完后暂停` | `write-stop`：`立即停止` |
| `paused` | `write-continue`：`继续写作` | `已暂停 · 12/37 章已完成 · 第 13 章未开始` | — |
| `stopping` | `write-stop` 置灰，文案 `正在停止…` | `正在停止，丢弃第 13 章未完成正文` | — |
| `stopped` | `write-continue`：`继续写作` | `已停止 · 第 13 章未完成正文已丢弃（8 条已完成章不受影响）` | `重写第 13 章` |
| `done` | `开始逐章审阅`（`write-start` 隐藏） | `全部 37 章已写完 · 待审阅 9 章` | 导出成稿 |

**映射规则（实现照抄）**：`pause_requested` → `data-state=running data-phase=pause-requested data-pause-pending=true`；`paused` → `data-state=paused`；`stopping` → `data-state=running data-phase=stopping`；`stopped` → `data-state=idle data-phase=stopped`；`done` → `data-state=idle data-phase=done`（同时渲染 `开始逐章审阅`）；`interrupted`（重启/断连）→ `data-state=interrupted`。

**工程约束**：`write-start` / `write-continue` 是同一个"启动连续 job"的动作，仅在 `idle/stopped/paused/done` 出现；`write-pause` 与 `write-continue` 互斥；`write-stop` 只在 `running/pause_requested` 出现。四个锚点**同一时刻至多一个可见**（QA 用 `locator.count()===1` 断言不会踩雷）。

### 7.3 进度真实性（照 SPEC §6.3，别编百分比）

- 章节进度 = `已完成章 / 总章数`（真实计数，允许百分比）。
- 当前章的"已 1,840 字"只有在服务端能给出时才显示；拿不到就只显示 `正在写第 13 章`，**不得**用前端计时器伪造字数。
- 时长：`data-elapsed` 由客户端每秒本地递增 + 每 2s 与服务端对账（对账只纠正不倒退）；超过 120s 无上游推进 → job 转 `failed`（`PROVIDER_TIMEOUT`）。
- "平均每章 / 剩余约 N 分钟"：只在**完成 ≥ 2 章**后显示，文案必须带口径 `按已写章平均计算`。完成 0–1 章时不显示（避免假预估）。

### 7.4 暂停 vs 立即停止（P-6 的落地）

| | 暂停 | 立即停止 |
|---|---|---|
| 语义 | 当前章写完后停；不丢任何内容 | 中断当前章；**丢弃该章未完成正文**（INV-3：零写入） |
| 二次确认 | **不需要**（安全操作） | **需要**，文案见下 |
| 完成后状态 | `paused`，已完成章全部保留 | `stopped`，当前章回 `pending`、`data-failed=false`、无正文 |
| 按钮位置 | 控制条左侧主按钮位 | 控制条右侧次按钮（`btn--ghost`），不与暂停同级强调 |

立即停止确认框（`danger-confirm` 结构，复用现有样式）：

```
停止连续写作？
第 13 章《纺织厂的雨》正在写，已生成 1,840 字，这部分不会保存。
已完成的 12 章（3.4 万字）不受影响，随时可以继续。
                                        [继续写作]   [立即停止，丢弃本章]
```

- 首焦在 **`继续写作`**（安全动作）；`Esc` = 继续写作。
- 若当前章还没有任何正文（刚起头）→ 确认框文案退化为 `停止连续写作？已完成 12 章会保留。`（不吓人）。

### 7.5 单章失败与恢复

- 失败只影响该章（SPEC §4.5）：其它章状态不变，job 继续写下一章（连续模式下**默认继续**，不因单章失败整体中断）。
- 行内呈现：状态徽标 `待写 · 失败` + `data-failed=true` + `data-error=PROVIDER_TIMEOUT`；行操作 `重试本章`。
- 顶部一条轻提示（不挡住整体进度）：`第 15 章没写成（供应商超时），其余章节继续写完 [重试第 15 章] [查看详情]`。
- 全部写完后若仍有失败章：`done` 状态不成立，控制条显示 `36/37 章完成 · 第 15 章失败` + `重试第 15 章` + `跳过第 15 章`；只有所有章进终态才算 `completed`。
- 重试只重跑该章，不重写已完成章（SPEC §7.4）。

### 7.6 写完之后：逐章审阅队列（W9）

入口：控制条主按钮 `开始逐章审阅`，或左栏「下一步」卡，或章节行 `审阅`。三者都跳 `写作台 /project/:id?review=1&chapter=<首个待审章>`。

**为什么审阅放在写作台而不是流水线页**：正文阅读/编辑需要现有编辑器（字号、AI 面板、自动保存、closeGuard），重造一套等于第二套编辑器。流水线页负责"进度与控制"，写作台负责"内容与终态"。这也是 R7 的原始意图（`/project/:projectId` 是 P4 的编辑器视图）。

```
┌ 写作台顶部 REVIEW 条（新增，sticky 在 topbar 下方） ──────────────────────────────┐
│ 审阅队列 · 第 2/9 篇 · 第 2 章《七天的约定》· 2,980 字（范围 2500–4000 ✓）          │
│                                        [上一篇] [下一篇]   [通过 ⌘↩] [退回重写]     │
│                                        [人工改后通过] [跳过本章] [重写本章]          │
└────────────────────────────────────────────────────────────────────────────────────┘
```

**审阅顺序**：按章序，跳过已终态的章；末篇时 `下一篇` 变 `完成审阅`（回到流水线页并 toast `9 篇已审完`）。
**退回重写**：必填意见（抽屉同 `FeedbackComposer`，作用域固定 `这一章`），提交后该章 → `changes_requested` 并立刻启动单章重写 job；正文区保留旧版本可读（禁空白），重写完成后回 `in_review` 并显示 `已按意见重写，可对比上一版`。
**人工改后通过**：编辑正文后点它 → `approved_manual`，自动记一条 `manual` 版本快照。
**跳过本章**：确认 `跳过会把这一章标记为"已跳过"（不计入完成字数），正文保持为空或现有内容。`
**通过**：`approved`，若该章有 `stale`/超范围标记仍允许通过（SPEC：超范围不阻断 REVIEW），但通过前给一次行内提示（非阻塞）。

**快捷键**：`⌘↩` 通过并下一篇、`⌘⇧↩` 退回重写、`[` / `]` 上/下一篇。快捷键提示只在 REVIEW 条 hover 时显示（不占常驻空间）。

**批量通过的取舍**：V1 **不提供**"全部通过"。理由：SPEC §4.5 要求每章人工终态，批量通过会把门槛变成一次点击的橡皮章。若用户确有需要，走待决 D7（默认不采纳，见 §15）。

### 7.7 章节版本的可见性（`chapter-version-list`）

- 行 `⋯` → `版本`，或 REVIEW 条 `版本`，打开右侧抽屉：版本列表（时间 + 来源 `AI 生成` / `按意见重写` / `你修改` / `确认快照` + 字数），可预览、可 `回到此版本`（生成新版本，不删历史）。
- 重写前自动快照（`snapshotChapter`，现有能力），所以"重写把好版本冲掉"不可能发生。
- 空态：`这一章还没有历史版本。`

### 7.8 刷新 / 重启恢复（`pipeline-banner[data-state=interrupted]`）

| 场景 | 用户看到 | 可做 |
|---|---|---|
| 生成中刷新页面 | 回来后控制条 `running` + 进度按持久化状态重建（可能落后 2s，不重头） | 暂停 / 停止 |
| 关闭页面再回来 | 同上（job 从未停止，INV-5） | 同上 |
| 应用崩溃/重启 | 顶部横幅 `上次写作被中断（写到第 13 章）· 已完成 12 章保留` | `恢复写作`（从第 13 章继续，不重写已完成章）/ `放弃`（只清 job，不删内容） |
| 阶段级中断（P1/P2/P3） | 同结构横幅，`恢复` 重跑未完成步骤 | 恢复 / 放弃 |

**禁令**：刷新后不得回到"什么都没发生"的空态（AUDIT R6）；不得要求用户重新点一次"开始写作"却从第 1 章重跑。

### 7.9 给 QA 的 S1 修订（D4 后必须改脚本）

SPEC §12.1 S1 的步骤 8–9 是"写完第 1 章就 approve / 第 2 章 request-changes"，与 D4 冲突。建议改为：

```
8. P4：点 write-start → 断言 write-start 消失、write-pause 可见
   → 等待连续生成把 5 章全部写完（chapter-row 全部 data-status=in_review）
   → 断言控制条 data-state=done、文案含「全部 5 章已写完」
9. 点 write-pause 的场景单独测（S1b）：启动后立即暂停 → data-phase=paused 或 pause-requested
   （data-state 此时为 paused 或 running，见 §7.2 映射规则）
9'. 点 write-stop 的场景单独测（S1c）：确认框出现 → 点「继续写作」取消；再点「立即停止」→
    当前章 data-status=pending 且 data-words 为空，已完成章不变
10. 审阅：点「开始逐章审阅」→ 进入写作台 review=1 → chapter-approve 第 1 章 →
    chapter-request-changes 第 2 章（填意见）→ 断言 changes_requested → chapter-rewrite →
    新版本 → chapter-version-list ≥ 2
11. 全部章终态 → pipelineStatus=completed
```

配套断言建议：`write-pause`/`write-continue`/`write-stop`/`write-start` 四者同页至多 1 个可见（§7.2 已保证）。

## 8. 短篇：没有章节，用节拍

短篇不是"章节少的长篇"，而是结构不同（SPEC §5）。界面必须**彻底不出现章节/卷**，否则用户会以为哪里坏了。

### 8.1 词表替换（按 SPEC §0 术语表）

| 长篇 | 短篇 | 说明 |
|---|---|---|
| 章节计划 | **节拍计划** | 阶段 3 的名称、面包屑、错误文案全改 |
| 章 / chapter | **节拍 / beat** | 行锚点 `beat-plan-row`（P3）、`beat-row`（P4） |
| 37 章 · 11.1 万字 | 8 节拍 · 1.2 万字 | 默认 8 节拍（范围 3–40） |
| 卷 | — | 不渲染 |
| 章节板 | 节拍板 | 布局相同，列名不同（"章"→"节拍"） |
| 逐章写作 | 逐节拍写作 | 控制条文案 `正在写第 3/8 个节拍` |
| `chapter-row` | `beat-row` | P4 断言：长篇 `beat-row` 计数=0，短篇 `chapter-row` 计数=0 |

### 8.3 各阶段差异

| 阶段 | 长篇 | 短篇 |
|---|---|---|
| P1 设定 | 世界观必填（世界规则至少 1 条）、环境 ≥1 | **世界规则可空**（默认 0 条）、环境可空；人物仍 ≥1；块头文案 `世界观（短篇可留空）` |

| P3 计划 | 表格（章） | 表格（节拍），锚点换 `beat-plan-row`，范围 3–40 |
| P4 写作 | 章节板 + 连续生成 | 节拍板 + 连续生成，控制条 `正在写第 3/8 个节拍` |
| 正文 | 卷 / 章 | 单篇：所有节拍正文按序拼成一个文档（写作台里显示为"节拍分隔线"而非章节列表） |
| 导出 | 按章导出 md | 导出单个 `.md`（标题 + 小节） |

### 8.4 短篇专属规则

- 短篇的 P4 若用户想"分组"，只允许在写作台用 `###` 小节标题，不引入"章"的概念。
- 作品类型在**创建后不可改**（改成短篇/长篇会重建结构）。若用户确实要改：设置里 `改变作品形态` → 警告 `会按新形态重建设定/大纲/计划，正文保留但不保证结构对齐` → 二次确认。
- 导航绝不显示 `章节` 字样；若某处漏了（如错误文案 `第 12 章生成失败`），短篇下必须替换为 `第 12 个节拍生成失败`（统一走 `unitLabel()` 工具函数，§11.5）。

### 9.2 错误卡规格（`plan-error[data-code]`）

结构固定四段，缺一不可：

```
┌────────────────────────────────────────────────────────────────────┐
│ ⚠ 生成失败：模型服务超时                                            │ ① 标题（人话）
│ 等了 120 秒没有响应，本次没有产出内容。已写的章节不受影响。          │ ② 说明（影响范围）
│ 供应商：DeepSeek · 模型：deepseek-chat · 生成任务 #j_8f2a           │ ③ 上下文（可复制）
│ [重试] [换个模型重试] [删除这个作品]                技术详情 ▾      │ ④ 动作 + 详情折叠
└────────────────────────────────────────────────────────────────────┘
```

- 技术详情展开：`code=PROVIDER_TIMEOUT`、`dur=120.0s`、`stage=p1`、`jobId`、`provider`、`model`、`requestId`，带 `复制诊断信息` 按钮（一次复制全文，方便用户发给客服/贴 issue）。
- **禁止**把 `502`、`The operation was aborted due to timeout` 这类原文当主文案（AUDIT R3：用户看到的就是这句）。
- 重试按钮的语义：`重试` = 同模型重跑；`换个模型重试` = 打开模型选择（`/settings` 或内联下拉）后再跑；`删除这个作品` = 二次确认后删（`danger-confirm`，这是真危险操作，用红色）。

**18 个错误码 → 界面映射**

| code | 标题（人话） | 说明要点 | 主操作 | 可重试 |
|---|---|---|---|---|
| `NO_DEFAULT_MODEL` | 还没选默认模型 | 去设置里选一个模型再回来 | `去设置` | 否（选完自动继续） |
| `NO_API_KEY` | 这个供应商还没填 Key | 填了 Key 才能生成 | `去填 Key` | 否 |
| `AUTH_FAILED` | Key 无效或已过期 | 这是供应商拒绝，不是网络问题 | `去检查 Key` | 否 |
| `MODEL_NOT_FOUND` | 模型不存在或已下线 | 该供应商已没有这个模型 | `换一个模型` | 否 |
| `REASONING_UNSUPPORTED` | 这个模型不支持推理等级 | 关掉推理等级，或换支持推理的模型 | `关掉推理等级并重试` | 是（改配置后） |
| `RATE_LIMIT` | 请求太频繁被限流 | 已自动重试过 1 次 | `稍后重试`（倒计时 xx 秒） | 是 |
| `PROVIDER_TIMEOUT` | 模型服务超时 | 等了 120 秒没响应，没有产出内容 | `重试` / `换个模型` | 是 |
| `PROVIDER_ERROR` | 模型服务报错 | 上游返回错误（含 5xx） | `重试` / `换个模型` | 是 |
| `NETWORK` | 网络不通 | 请检查网络或代理 | `重试` | 是（自动重试 1 次） |
| `EMPTY_OUTPUT` | 模型没有返回内容 | 常见于推理模型把内容放进了思考字段；已记录诊断 | `重试` / `换个模型` | 是 |
| `INVALID_JSON` | 返回的内容不是合法结构 | 已保留原始返回，可在诊断信息里看 | `重试` | 是 |
| `CONTENT_BLOCKED` | 内容被供应商拒绝 | 换个说法或换个模型 | `改意见后重试` | 是 |
| `QUOTA_EXCEEDED` | 额度用完了 | 去供应商充值或换 Key | `去检查额度` | 否 |
| `CANCELLED` | （不是错误）已取消 | 保留已生成的部分 | `继续企划` | — |
| `INTERRUPTED` | 生成被中断（应用重启） | 已完成的都保留了 | `从断点继续` | 是 |
| `STAGE_LOCKED` | 还不能做这一步 | 请先确认上一阶段 | `去确认「设定」` | 否 |
| `CONCURRENT_JOB` | 已经有一个任务在跑 | 等它完成，或先取消它 | `查看正在跑的任务` | 否 |
| `MIGRATION_FAILED` | 旧作品升级失败 | 原数据未改动，可重试或先备份 | `重试升级` / `导出备份` | 是 |

- 错误卡**按阶段出现**（P1 错误出现在 P1 区，不整页替换）：左栏轨道始终可用，用户能切到别的阶段看已有内容。
- 错误持久化：刷新后 `plan-error` 仍在（读 `project.lastError`），直到重试成功或用户手动关闭（`知道了`，仅当错误无后续动作时才给）。
- 失败一律 toast 一条 `toast--warn`（3s）+ 卡片常驻；成功 toast 只有 1.8s。

### 9.3 两级前置拦截（无 Key / 无默认模型）

**一级：新建弹窗内联预检**（`new-project-precheck`）

- 弹窗打开即调预检；不通过时：
  ```
  ⚠ 还不能让 AI 企划：没有可用的默认模型
     [去设置里选模型]     仍然创建（只能自己写）
  ```
- `仍然创建` 可用（不阻断创建），但创建后 P1 进"待生成 + 说明"而不是自动跑 job（避免又出现"点了没反应"）。
- 通过时显示 `✓ 将使用 DeepSeek · deepseek-chat`（一行，让用户知道即将用哪个模型）。

**二级：页内 banner**（`pipeline-banner`）

- 全局模型配置在会话中被改坏（Key 失效）→ 流水线页顶部 banner：`模型不可用：Key 无效。企划暂停在「设定」。[去设置]`，同时禁用所有生成按钮（tooltip 说明原因）。

### 9.4 加载与超时（三段式，禁止一步到"失败"）

| 时长 | 界面 |
|---|---|
| 0–2s | 骨架 + `正在生成设定…`（不显示秒数，避免 0 秒闪动） |
| 2–60s | 秒数计时 + `通常需要 20–60 秒` + `取消` |
| 60–115s | 秒数变 warn 色 + `比平时久，还在等（模型可能较慢）` + `取消` 高亮 |
| ≥120s | 服务端已超时 → 错误卡 `PROVIDER_TIMEOUT`（不自己编造超时；前端 120s 只做"提示"，不改状态） |
| 轮询失败 ≥3 次 | 控制条 `· 与后台失去联系`，不切错误卡 |

### 9.6 离开页面保护（三处，各管一件事）

| 位置 | 拦什么 | 不拦什么 | 实现 |
|---|---|---|---|
| 应用内路由离开（点 rail/tab/返回） | **未保存的手工编辑**（条目编辑态、章节正文脏数据） | 后台 job（INV-5 不中断） | 路由守卫 + 统一确认弹窗 `有未保存的修改，先保存？[保存并离开][丢弃][取消]` |
| 浏览器 `beforeunload` | 同上 | job | `event.preventDefault()` |
| 桌面关窗（`closeGuard`，现有 `desktop.ts`） | 同上 + 保存失败 | job | 复用现有 `closeGuard(hasUnsaved)`；保存失败时"不关窗"（v0.1.11 已定的语义） |

- 顶栏 job 条在用户离开流水线页时**不消失**（全局 job 条挂在 AppShell 顶栏，跨页可见）：`设定生成中… 12 秒`。这是"关页面不取消"的可见证据。
- 明确文案：`离开页面不会中断生成，作品已保存`（出现在 P-6 的三处：新建后 15s 提示、控制条 tooltip、离开确认框次要说明）。

|---|---|
| 同项目已有 job（`CONCURRENT_JOB`） | 按钮点击后 toast `已有任务在跑：[设定生成中 12 秒]，等它完成或先取消`，并高亮 job 条 |
| 阶段未确认就想确认下游（`STAGE_LOCKED`） | blocker 行 + 按钮 disabled（正常路径不会触发；触发即说明状态不同步，页面自动刷新一次） |
| 迁移进行中用户操作 | 迁移页模态锁（`migration-banner[data-state=failed|done]`），期间禁止发起生成 |
| 多窗口同项目（桌面端） | 不做实时协同；后写入者覆盖前写入者时，若检测到版本不匹配 → toast `内容已被另一个窗口更新，已刷新为最新版本` |

## 10. 状态与文案契约（前端实现即照此写）

### 10.1 阶段徽标

| 状态值 | 徽标文案 | 视觉 |
|---|---|---|
| `empty` | `待生成` | 灰点 + 次要色文字 |
| `generating` | `生成中` | 呼吸圆点（accent）+ `· 12 秒` |
| `review` | `待确认` | accent 描边 chip |
| `confirmed` | `已确认` | 绿点 + 次要色 |
| `failed` | `生成失败` | 红 `!` + 可点 |
| `skipped` | `已跳过` | 灰斜体 |

### 10.2 章节状态（`chapter-row[data-status]` / `beat-row[data-status]`）

| 值 | 徽标 | 附加属性 |
|---|---|---|
| `pending` | `待写` | 失败时 `data-failed=true` + 行内红点 `第 12 章生成失败` |
| `generating` | `写作中` + 迷你进度 | `data-queued=false`（当前章）；排队中行仍是 `pending` + `data-queued=true` |
| `in_review` | `待审阅` | `data-words=<实际字数>` |
| `approved` | `已通过` | — |
| `changes_requested` | `需修改` | 附最近意见摘要（截断 1 行） |
| `approved_manual` | `人工通过` | — |
| `skipped` | `已跳过` | — |

**关于"排队"**：D4 下会有大量章处于"已排进本次连写、还没轮到"。规则：**不新增状态值**，用 `pending` + `data-queued="true"` 表达，UI 徽标仍是 `待写`，只是行尾多一个淡色 `排队中` 小字。好处：QA 的 `data-status` 断言集合不变（SPEC §11 不得改名/删减）。

### 10.3 颜色语义（只借现有 token，不新增色）

| 语义 | token/类 | 用在哪 |
|---|---|---|
| 主行动 | `--accent` | 确认、开始写作、通过 |
| 成功/已确认 | `--ok`（若不存在，用 `.tag--ok` 现有绿） | 已确认、已通过、偏差 ✓ |
| 提醒 | `--warn` / `.toast--warn` | 偏差 10–25%、60s+ 计时、生成比平时久 |
| 阻断 | `--danger` | 偏差 >25%、失败、删除 |
| 中性/未开始 | `--muted` | 待生成、待写 |

**不要新造颜色变量**：CSS 里没有的变量写上去是无效声明，元素安静继承父色，构建不报错（本项目踩过）。新增视觉只在 `.pipeline-*` 内用已有 token 组合。

### 10.4 无障碍与键盘

- job 条：文本容器 `role="status" aria-live="polite"`；**只有阶段名/状态变化才播报**，秒数容器 `aria-hidden="true"`（否则每 2 秒打断读屏）。
- 进度条：`role="progressbar"` + `aria-valuenow`（章数，非百分比）+ `aria-valuemin=0` + `aria-valuemax=total` + `aria-label="写作进度：11/37 章"`。
- 焦点管理：切阶段不抢焦点（保持在 tab 序列首位）；打开抽屉后焦点进抽屉，`Esc` 关闭并**回到触发按钮**；确认弹窗首焦在"取消"。
- 键盘：`⌘↩` 通过并下一篇、`⌘⇧↩` 退回、`Esc` 关闭浮层；表格行 `Enter` 打开大纲抽屉；`j/k` 上下移动章节（可选，V1.1）。
- 动效：`prefers-reduced-motion: reduce` 时取消呼吸点/骨架 shimmer，保留静态文本与秒数。
- 触屏：所有 hover-only 操作（条目卡操作行）在窄屏常显；最小点按 32px。

### 10.5 Toast 规范

| 类型 | 时长 | 例子 |
|---|---|---|
| 成功 | 1.8s，可叠加但同类去重 | `已保存（修订 #13）`、`已按意见重做` |
| 提示 | 3s | `已在本章写完后暂停` |
| 警告 | 5s + 手动关闭 | `1 条重生成失败 [重试]` |
| 错误 | 5s + 手动关闭 | 与错误卡并存，toast 只是提醒 |

同一秒内同类 toast 只显示最新一条（避免连续写时刷屏 `已保存`）。

### 12.4 轮询策略（前端实现即照此）

| 条件 | 间隔 | 停止条件 |
|---|---|---|
| `job.state === 'running' \| 'pausing'` | 2s | 状态变化或页面卸载 |
| `job.state === 'paused'` 且用户停留在页 | 10s（防止后台被别处推进） | — |
| 无 job、阶段 `review` | 5s（感知其他窗口/后台变更，V1 可关） | — |
| 连续失败 3 次 | 停止，控制条降级 `与后台失去联系`，提供 `重试连接` | 用户手动重试 |
| 页面隐藏（`visibilitychange`） | 暂停轮询，回前台立即拉一次 | — |

SSE（SPEC §6.5 允许）作为 V1.1 优化：`GET /api/jobs/:id/stream`，事件 `stage-progress`，轮询作为降级。**禁止**用 SSE 的"上次进度"做假进度条（进度只能来自服务端真实计数）。

### 12.5 错误映射（前端只认 code）

```ts
// lib/errors.ts
const MAP: Record<ErrorCode, { title: string; body: string; primary: Action; secondary?: Action; retryable: boolean }>
```

规则：① 前端**不解析 `message`**（中文/英文/堆栈都不可控）；② 未知 code → 通用卡 `生成失败` + 技术详情折叠（永远有出路）；③ `retryable=false` 的码不显示 `重试` 按钮（避免用户点了没反应——AUDIT R1 的病）。

## 14. 场景 ↔ 界面对照（QA 写脚本时看这张）

| 场景 | 对应界面与断言点 |
|---|---|
| S1 长篇黄金路径 | 已按 D4 修订（§7.9）：连续写到 3 章 `in_review` → 暂停/继续 → 审阅模式逐章 |

| S4 上游变更 stale | `pipeline-banner[data-state=stale]` + `stage-stale-banner` + 三选项（`stage-stale-keep` / `stage-stale-regenerate` / `stage-stale-ignore`）；**下游阶段即使已 `confirmed` 也要渲染**（文案「上游已变更，建议复核后再确认」，P2 保持 `confirmed` 不回滚）；点"按上游重排"后 P2 回 `stage-p2[data-status=review]`；**上游未确认时该键 disabled 且出现 `stage-stale-regenerate-hint`（「先确认上一阶段」），不得点出 409** |

| S7 并发 | 两次点 start → 第二次 toast `已有任务在跑` + `CONCURRENT_JOB`，job 数量仍 1 |
| S8 重启恢复 | 杀服务再起 → `pipeline-banner[data-state=interrupted]` + `从断点继续` → 继续后 `data-state=running` |

| S11 暂停止损 | `write-stop` 二次确认 → 取消 → 确认后当前章 `pending` 且无 `data-words` |
